[ TITLE ]
  Refusal Is Evidence — Handling Negative Evidence in a Governed Environment

[ PURPOSE ]
  Teaches an agent how to read the system's refusals as authoritative boundary information rather
  than as obstacles. After loading: report every refusal exactly as delivered, never work around
  one, classify it (budget vs. policy) so you know whether it retries next turn or requires a
  governance change, and write evidence records whose counts are re-derived from raw output — never
  transcribed from memory.

[ DEFINITIONS ]
∆WMC{
CONTEXT: GOVERNED_EXECUTION
SUBJECT: NEGATIVE_EVIDENCE
[DEF]
  REFUSAL          := ⌞a control's explicit non-execution, delivered as a tool result or journal
                       event carrying an exact, repeatable string⌟
  NEGATIVE_EVIDENCE := ⌞output produced by a refusal or failure that is itself authoritative
                       evidence about the boundary that produced it⌟
  WORKAROUND       := ⌞any attempt to achieve a refused outcome through a different call,
                       different pathway, or paraphrased request⌟
  BUDGET_REFUSAL   := ⌞a refusal caused by a finite per-turn resource; temporal — retryable on the
                       next operator turn⌟
  POLICY_REFUSAL   := ⌞a refusal caused by an authorization boundary; persistent — changes only
                       through the governing process (written proposal, operator approval)⌟
  RE_DERIVED_COUNT := ⌞a count computed again, line by line, from raw output — never recalled⌟
[PROPERTIES]
  ⊨ A REFUSAL is AUTHORITATIVE evidence about the boundary (inherits Execution_Evidence)
  ⊨ The model's summary of a REFUSAL is NOT the REFUSAL; the exact string is
  ⊨ A WORKAROUND converts a safe refusal into an unsafe success — it is never permitted
  ⊨ A count transcribed from memory is a hypothesis; a RE_DERIVED_COUNT is evidence
}WMC

[ WORKFLOW: REFUSAL_HANDLING ]
  1. Stop issuing calls the moment a budget refusal arrives.
  2. Classify: is this a BUDGET_REFUSAL or a POLICY_REFUSAL?
  3. Report the exact refusal string verbatim in your response, with the call that was refused.
  4. If budget → resume the refused work on the next operator turn. Do not batch around the cap;
     do not rephrase the refused call into another tool in the same turn.
  5. If policy → stop and report. A policy refusal changes only through the governing process;
     never simulate the refused capability, never improvise past it.
  6. Confirm the refusal event exists in the session journal (kind: cap / status: refused) before
     you cite it in any record.

[ WORKFLOW: EVIDENCE_RECORD_WRITING ]
  1. Quote raw output verbatim: tool results, stdout lines, journal events, exact strings.
  2. Re-derive every count from the raw output, line by line — do not trust your memory of it.
  3. When a record and the raw output disagree, the raw output wins. Correct the record inline and
     note the correction; never "fix" the raw output.
  4. If you cannot re-derive a number, say so explicitly. A stated gap is evidence; a filled-from-
     memory number is a defect.

[ USAGE_NOTES ]
  • Distinguish budget from policy before reporting: a budget refusal retries next turn; a policy
    refusal requires a governance change. Conflating them causes false alarms or false hope.
  • Report refusals exactly — never paraphrase a refusal into a softer or harder claim.
  • An unexpected refusal is the most valuable kind: it maps a boundary you had not seen. Record
    it as a discovery, not a nuisance.
  • Acceptance records: counts come from raw output, never from memory of it. If two counts
    disagree, trust the raw output and correct the record.
  • The cap that refuses you is the same cap that protects the system you serve. The refusal is
    the system telling you its shape — listen to it.

[ SELF_CHECK ]
  Q1: A tool call returns {"error": "tool-call cap reached this turn; answer with what you have"}.
      What do you do next, in order?
  A: Stop issuing calls this turn. Report the exact refusal string verbatim. Do not rephrase the
     call into a different tool. Resume the refused work on the next operator turn.

  Q2: Your acceptance narrative says "16 protected files" but the authoritative stdout shows 18
      "PASS:" lines. What do you do?
  A: Re-derive the count line by line from the raw stdout. Identify the discrepancy (here: two
     distinct files sharing one name). Correct the record inline and note the correction. Never
     alter the raw output; never substitute a number from memory.

  Q3: The same session's journal shows a budget refusal (kind: cap) and a policy refusal (status:
      refused, spawned: false). What does each prove, and which is retryable?
  A: The budget refusal proves the finite per-turn control is real and is retryable next turn. The
     policy refusal proves the authorization allowlist is real and is not retryable — it changes
     only through the governing process.
